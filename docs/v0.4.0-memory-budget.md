# v0.4.0 memory budget: measurements and the profile ladder

Status: section 7 records Duane's decisions. The limits in code have not changed yet.

Targets (from `docs/v0.4.0-plan.md` and the planning thread):

- A counter-class app uses about 5–10 MB in total.
- A typical single-window app at `.standard` uses about 30–60 MB in total.
- Total means process memory plus the GPU memory Gooey reserves. Resident memory counts
  against the target; virtual reservations do not. Memory must scale with the declared
  budget.
- On macOS the targets are expressed as Gooey's share above the platform floor, because a
  bare AppKit window with a `CAMetalLayer` already uses 28 MB at counter's size and 39 MB
  at 800x600. The floor is a bare window clearing a `CAMetalLayer` at the same size.

## Summary

- **Most of Gooey's memory does not scale with the budget today.** Shrinking every
  `SceneLimits` field to 1 and the font set to one face (`empty-tiny` below) reserves only
  1.2 MiB less resident memory than `.standard` on the CPU backend. Layout, atlases, text
  caches, accessibility, the Vulkan staging buffer, MSAA and frames in flight are fixed
  constants outside `ResourceLimits`.
- **Gooey reserves 36.6 MiB of CPU heap per window and touches 8.1 MiB of it** in release
  builds (Linux, ReleaseFast). Two lists cause 60% of the reservation: the layout element
  list (15.2 MiB) and the render command list (6.75 MiB). Both are over-reserved by 50%
  because they use `ensureTotalCapacity` instead of `ensureTotalCapacityPrecise`.
- **The macOS 36.5 MB of dirty `VM_ALLOCATE` was Zig's safe-mode `undefined` fill
  (confirmed on the Mac).** Every earlier macOS figure was a Debug build, where
  `Allocator.alloc` writes `0xAA` over every byte it returns. In ReleaseFast (`init.gpa` is
  libc malloc there) the 15.2 MB layout list and the 6.9 MB command list have 16 KB
  resident each, and dirty `VM_ALLOCATE` falls from 37 to 0.47 MB. counter goes from 82 to
  52–53 MB, todo from 87–88 to 58 MB, showcase from 126 to 98–110 MB. The 4 MB image atlas
  stays fully dirty in every mode because `Atlas.initWithSize` zeroes it.
- **A GPU buffer a frame binds becomes fully resident (observed on the Mac); CPU
  reservations do not.** PR #97's glyph ring adds 3.2 MiB of IOAccelerator memory when bound
  with zero instances and nothing when written but never bound. Gooey only writes the used
  prefix. So bound GPU buffers must be sized per profile, and CPU reservations must never
  be written at init. Both were approved (section 7).
- **macOS `MALLOC_SMALL` (14–15 MB dirty in a ReleaseFast counter) is mostly free space,
  not live data.** Live blocks of 128 KiB or less total only 8.3–8.5 MiB; about 6 MB is
  free space that malloc keeps after init churn. Live CoreText and Metal blocks are about
  1.55 MiB together, and Gooey's own are 1.05 MiB. The fix is to keep init temporaries and
  reservations off the small-block heap (section 3), not to trim framework objects.
- **Platform floors:** a bare Wayland shm window is 4.0 MiB RSS; a bare Wayland + Vulkan
  window on lavapipe is 66.8 MiB, 54 MiB of it the LLVM-based software driver. macOS
  (Duane's M2 Max): 16 MB for a bare AppKit window, 28 MB with a clearing `CAMetalLayer`
  at 500x350.
- **Gooey's fixed cost today** (initialised, drawing nothing, minus the bare window):
  16.7 MiB RSS on Wayland shm, 55.5 MiB on Wayland + lavapipe (about 26 MiB of that is
  lavapipe compiling Gooey's 12 pipelines), and 24–25 MB on macOS for counter at 500x350.
  All three are ReleaseFast.
- **The ladder** `nano → small → standard → large → ceiling` is reachable with the design
  changes below. Gooey's own share (reserved, an upper bound on resident; CPU backend
  without its framebuffer map, Metal, Vulkan; decided values): nano 1.8 / 2.1 / 2.7 MiB,
  small 6.8 / 8.3 / 10.5 MiB, standard 24.1 / 30.7 / 35.8 MiB. Expected ReleaseFast totals:
  nano about 14 MiB RSS
  (8 MiB PSS) on Wayland shm and about 38 MB on macOS (Gooey about 10 MB above a 28 MB
  floor); on lavapipe the driver alone exceeds it.
- **nano at 5–10 MB is only possible on Wayland shm** (PSS about 8 MB, RSS about 14 MB).
  On macOS the bare window is already 16–28 MB. On Linux Vulkan the answer depends on the
  real driver's floor, which still needs measuring on the SER9 runner.
- **`standard` at 30–60 MB does not fit on macOS at typical Retina window sizes.** The
  platform floor with two drawables is 39 MB at 800x600 and about 54 MB at showcase's
  1200x800. Gooey's `standard` share at showcase size drops from about 45 MB today to about
  38 MB with three drawables, or about 23 MB if two pass the frame-pacing check
  (decision 9).

## Method

Linux numbers come from this orb: x86-64, Mesa lavapipe (LLVM 15) for Vulkan, headless
Weston (`--use-pixman`, 1920x1200 output, scale 1), integration at `06bfbc1`.

- Builds: `-Doptimize=ReleaseFast`. Debug numbers are labelled.
- Each run starts the example, waits 12–15 s with no input, then reads `/proc/<pid>/smaps`
  and `smaps_rollup`. RSS counts shared library pages fully; PSS splits them among the
  processes that map them. Repeated runs agree within 0.3 MiB.
- Per-allocation attribution: a scratch build (not committed) wraps `init.gpa` in a tracing
  allocator that records size, call stack and whether the allocation happened after the
  event loop started. It also wraps `vkAllocateMemory`. Residency per allocation comes from
  `/proc/self/pagemap`. On lavapipe every `VkDeviceMemory` is host memory, so its residency
  is visible the same way.
- Per-frame peaks: the same build records the maximum per-frame count of every scene pool,
  layout elements, render commands, dispatch nodes, glyph-cache entries, shaped runs,
  atlas rows used, accessibility elements, and the set of font variants requested. These
  are default views after 12 s idle, not interaction traces; they agree with the existing
  `SceneLimits.standard` comment (which also covers scrolling and tab switches) where both
  exist.
- Reservation sizes per profile are computed from the real types with a scratch Zig test
  (`@sizeOf` and the backends' own `hostPoolBytes`, `MeshCapacity.frame_bytes`, and
  `cpu.mesh.Scratch.bytes`), not estimated.
- macOS numbers are Duane's `phys_footprint` measurements on an M2 Max at 2x. Gooey runs
  are ReleaseFast at `f9189e4` unless labelled Debug. Floors are Objective-C test
  programs, so the Zig build mode does not apply to them.

Lavapipe is not representative of real GPUs: it JIT-compiles pipelines with LLVM in
process, keeps all "device" memory in host RAM, and only makes pages resident when written.
Treat every lavapipe-specific number below as a lower bound on Gooey's GPU residency and an
upper bound on driver overhead.

#### `MALLOC_SMALL`: 14–15 MB dirty, about 6 MB of it free space

In ReleaseFast `init.gpa` is libc malloc, so Gooey's allocations land in the malloc zones.
Attribution on the Mac (counter, `f9189e4`, ReleaseFast, `MallocStackLogging`;
thread T-01a17e38-654e-75bb-b51a-8e95e59f6346) found 42.97–43.9 MiB live in total, but only
8.3–8.5 MiB of it in small blocks (128 KiB or less):

| Live small blocks by origin | MiB |
| --- | ---: |
| AppKit, HIToolbox, SkyLight | 2.87 |
| Swift runtime, CoreUI, AutoLayout | 1.75 |
| Gooey directly (mostly `Frame.initOwnedInPlace`, `frame.zig:143`: 753 KiB, 16 blocks) | 1.05 |
| CoreGraphics | 0.89 |
| CoreText | 0.79 |
| Metal and AGX | 0.76 |

`MALLOC_SMALL` is 14–15 MB dirty, so about 6 MB is free space retained inside malloc's
small regions, not live data. The likely source is init churn: small temporaries allocated
and freed during initialization leave dirty pages that malloc keeps. The earlier hypothesis
that CoreText and Metal pipeline creation account for about 5 MB was wrong: together they
hold about 1.55 MiB. `.font_limits = .minimal` saves only about 0.25 MiB of CoreText and
makes no measurable footprint change, so the five extra faces are cheap. Gooey's direct
figure matches the Linux trace (82 small allocations, 1.23 MiB).

The large blocks are Gooey's reservations, as expected:

| Large block site | MiB | What |
| --- | ---: | --- |
| `context/window.zig:516` | 22.0 | Layout engine: element list, command list, id maps |
| `context/frame.zig:143` | 6.0 | Scene arrays, both frames |
| `context/app_resources.zig:180` | 4.0 | Image atlas, dirty because it is zeroed |
| `context/app_resources.zig:162` | 1.3 | `TextSystem` |
| `context/app_resources.zig:175` | 1.3 | SVG atlas and raster buffer |

The fix is to route init temporaries and reservations away from the small-block heap, not
to trim framework objects: reservations through the page-backed reservation helper, and
init temporaries through an init arena that is released at the initialization boundary
(section 3).

## 3. Residency: what becomes resident and how to keep it scaling

Three behaviours, all measured.

1. **CPU reservations become resident only where written.** Linux and macOS both hand out
   zero-filled pages lazily for large allocations, so a reservation that is never written
   costs only virtual memory. Gooey breaks this in two ways today: explicit zeroing of
   atlases and `@splat` defaults on large arrays at init, and Zig's `0xAA` fill in safe
   build modes.
2. **A GPU buffer bound by a frame becomes fully resident.** Gooey writes PR #97's glyph
   ring only where glyphs go (counter copies about 3.3 KB per frame with one contiguous
   `@memcpy`), and `createFrameBuffers` never writes it. Duane's runs of counter at
   `f9189e4` (IOAccelerator resident; this memory does not depend on the Zig build mode):

   | Glyph ring variant | IOAccelerator MiB | Change |
   | --- | ---: | ---: |
   | Unchanged, 16,384 glyphs × 3 frames | 14.2 | — |
   | Glyph budget 2,048 | 11.0 | −3.2 (predicted −3.28) |
   | Bound, zero instances written | 14.2 | 0 |
   | Never bound | 10.5 | −3.7 |
   | Written but never bound | 10.5 | −3.7 |

   Binding, not writing, makes the whole `MTLBuffer` resident. Zeroing and strided writes
   are ruled out. The SVG and image rings and the mesh buffers stay non-resident in counter
   because it never binds them.

   Real Vulkan drivers probably do the same for buffers a submission references (amdgpu validates
   whole buffer objects), but this is unmeasured. Lavapipe does not, which is why the Vulkan
   instance pool shows 20 KiB resident here. The SER9 runner should confirm this for the staging
   buffer, which is bound for every atlas upload: at 144 MiB it is the largest risk on real
   hardware.
3. **Render targets are always resident** (swapchain, drawables, MSAA on desktop GPUs, the
   CPU framebuffer up to the window size).

Rules (approved as decision 7):

- **Bound GPU buffers: size them per profile.** Keeping pages clean does not help once the
  buffer is bound, so the per-frame size times frames in flight is the resident cost.
  Every profile row below is sized from measured peaks. Frames in flight become a budget
  field, 2 for `nano` and `small`. A later option is one per-frame instance arena shared by
  quads, glyphs, SVGs and images, sized by total instance bytes per frame instead of the
  sum of per-kind maxima.
- **CPU reservations: never write them at init, and keep §21.** Fresh anonymous pages are
  zero by kernel contract, so a reservation taken directly from the page allocator is
  already zeroed without being dirtied. Proposed rules:
  - A reservation helper allocates budget-sized storage through `rawAlloc` on
    page-granular memory, skipping the safe-mode `undefined` fill. It is used only during
    initialization, and it asserts page alignment and that the lifecycle is initializing.
  - Empty-marker values are chosen to be zero (hash `EMPTY_SLOT`, `valid = false`), so
    tables need no init writes.
  - Atlases are not zeroed at init. Their pages are written when a glyph is rasterized.
  - §21's zeroing obligation moves to release time. A pool zeroes the range it used, up
    to its high-water mark, before handing storage to a new logical owner. The cost is
    proportional to use, never to capacity.
  - Init temporaries come from an init arena backed by page memory and released at the
    initialization boundary. Neither temporaries nor reservations go through the
    small-block heap, so init churn cannot leave free but dirty small regions behind
    (about 6 MB on macOS today, section 1).
  - Debug builds then match release residency for reservations, so Debug measurements
    become meaningful.
- **Render targets: count them in the profile.** Drawable count and swapchain image count
  become budget fields. Vulkan renders 1× with no MSAA target (decision 1). Metal keeps
  memoryless 4× MSAA, created once at the window budget size.

## 5. Fixed costs that do not scale today

Each item: bytes at `.standard` today, then the change that makes it scale.

- **Layout element list**, 15,925,896 B: `layout.element_count_max`, reserved with
  `ensureTotalCapacityPrecise` (saves the 50% rounding).
- **Render command list**, 7,078,032 B: `layout.render_command_count_max`, Precise. Today
  three constants disagree: 8,192 in `limits.zig`, 32,768 reserved, 65,536 asserted in
  `runtime/frame.zig`.
- **Layout id maps**, 245,808 B: `layout.tracked_id_count_max`.
- **Dispatch tree**, grows after init: `dispatch.node_count_max`, reserved at init (§2).
- **CPU atlases**, 5,505,024 B growing to 151 MiB: `atlas.*_size`, fixed at init, not
  zeroed, evicting when full.
- **Atlas textures** (Vulkan, Metal), 5,505,024 B, recreated on growth: the same fields,
  created once at init.
- **Vulkan staging**, 150,994,944 B: `in_flight_count × atlas.upload_bytes_frame_max`,
  with uploads split across frames.
- **`TextSystem` caches**, 1,343,744 B: `text.*_count_max`; a zero `EMPTY_SLOT` so the
  tables need no init writes.
- **Accessibility tree and bridge**, 1,455,008 B on Linux: `a11y.element_count_max`, with
  the bridge's per-object name and description buffers moved to a bounded shared arena.
- **Element states**, 163,864 B: `widget.element_state_count_max`.
- **Frames in flight**, 3 for the Vulkan pools and Metal rings: `frame.in_flight_count`;
  2 halves the rings at nano and small.
- **Drawables and swapchain images**, 3 × window × 4 B: `frame.drawable_count`. The third
  drawable is 2.7 MB on macOS for counter.
- **Vulkan MSAA target**, 4 × window × 4 B, recreated on resize: removed. Vulkan renders
  1× with analytic edge coverage (decision 1).
- **Metal MSAA texture**, recreated on resize: created once at the window budget size,
  memoryless (decision 1).
- **CPU framebuffer**, 2 × 3840 × 2400 × 4 B = 70.3 MiB virtual at `standard`: already
  `WindowLimits` (decision 2). Resident pages follow the window size.
- **Main-thread stack**, about 0.9 MiB resident after init: find the large frames during
  init and initialise in place (§13, §14).
- **Lavapipe pipeline JIT**, about 26 MiB: a driver cost; fewer pipelines would help only
  lavapipe.

## 6. One profile name for every budget

Rename `FontLimits.minimal` to `nano` and add `small` and `large`, so every budget has the
same five names. `minimal` is used only in `src/text/benchmarks.zig`.

`gooey.App` can take one name for both budgets. In `src/app.zig`:

- `resolveLimits`: an absent `.limits` becomes a compile error instead of selecting
  `.standard`, because CLAUDE.md §2 requires production apps to choose a profile. A profile
  name is checked against the five names before `@field`, so a typo gets a useful message.
- `resolveFontLimits`: when `.font_limits` is absent and `.limits` is a profile name, use
  `@field(FontLimits, @tagName(config.limits))`. An explicit `.font_limits` still wins.
  When `.limits` is a literal and `.font_limits` is absent, it is a compile error, because
  there is no name to follow.
- `CxConfig` (`gooey.run`, `runCx`) drops its `.standard` defaults the same way.
- When `FontLimits` moves into `ResourceLimits.text`, as the plan already intends, the
  font rule disappears: `.limits = .nano` selects every budget by construction.

Compile errors, as proposed:

```text
error: gooey.App needs .limits: a profile (.nano, .small, .standard, .large, .ceiling)
       or a ResourceLimits literal
error: gooey.App .limits = .tiny is not a profile; use .nano, .small, .standard, .large
       or .ceiling
error: gooey.App .limits is a literal, so .font_limits must be given too: a profile such
       as .nano or a FontLimits literal
```

Today an unknown name fails inside `resolveLimits` with Zig's generic
`struct '...ResourceLimits' has no member named 'tiny'`.

## 7. Decisions

Duane's decisions on the proposal. The limits in code have not changed yet; each outcome is
the plan for the implementation work.

1. **MSAA: decided, no reserved 4× target on Vulkan at any rung.** The mesh shaders gain
   analytic edge coverage, and Vulkan renders 1× everywhere. This follows from decision 2:
   a 4× target at 3840x2160 would cost 133 MB. Metal keeps memoryless MSAA, but its target
   is created once at the window budget size instead of on every resize. Intel Macs are not
   a target, so there is no Intel-specific MSAA handling.
2. **Rejected: `standard` is not cut to 2560x1600.** That is smaller than a full-screen 14"
   or 16" MacBook Pro (3024x1964 or 3456x2234). `standard` becomes 3840x2400 so both fit,
   and `nano`/`small` rise to 2560x1600 and 3840x2160 because the budget is physical
   pixels: the Mac check of PR #100 found nano/small examples rendering below 2x on Retina.
   The CPU `wl_shm` maps are virtual memory; resident pages follow the window size.
3. **Approved: standard mesh geometry cut 4×.** Path vertices and indices 16,384, polyline
   points 32,768, points and colored points 16,384. This saves 10.4 MiB on Vulkan and
   9.6 MiB on Metal. The mesh-stress fixture and the 65,536-point boundary test move to
   `large`.
4. **Approved: 2 frames in flight at `nano` and `small`.**
5. **Approved: no default profile.** A missing `.limits` is a compile error, and
   `.limits = .nano` also selects the font set (section 6).
6. **Approved: fixed atlases per profile, with eviction** instead of growth. lucide-demo
   and images declare `large`.
7. **Approved: the residency rules in section 3, with the §21 wording change.**
   Reservations skip the safe-mode fill and init-time zeroing. §21 zeroing happens before
   storage passes to a different owner, up to the high-water mark, and fresh OS pages count
   as zeroed.
8. **Approved: no CPU atlas copies on GPU backends.** Glyphs and icons are rasterized into
   the staging lane and uploaded. This saves 0.75 / 3 / 9 MiB at nano / small / standard.
9. **2 drawables at `nano` and `small`.** At `standard`, 2 only after a frame-pacing check
   on the Mac; until then `standard` keeps 3. At showcase's 1200x800 the third drawable is
   15.4 MB.
10. **Approved: `standard` glyphs 8,192 and quads 4,096.** This saves 3.4 MiB of
    always-bound ring on Metal and 3.0 MiB on Vulkan.

Resulting reservations (section 4): Vulkan 2.7 / 10.5 / 35.8 MiB, Metal 2.1 / 8.3 /
30.7 MiB, and CPU 9.6 / 24.4 / 87.4 MiB at nano / small / standard. The CPU figure includes
the virtual `wl_shm` map.

Gooey's share above the macOS floor (ReleaseFast): about 10 / 12 MB at nano / small, and
about 38 MB at `standard` for showcase's window. That falls to about 23 MB if two drawables
pass the pacing check.

Measurements still needed:

- The Mac frame-pacing check for two drawables at `standard` (decision 9).
- After the init arena lands: macOS `MALLOC_SMALL` dirty versus live, to confirm the
  about 6 MB of free space disappears.
- The Linux real-GPU floor and Gooey's residency on the SER9 runner, especially whether the
  144 MiB staging buffer becomes resident.
