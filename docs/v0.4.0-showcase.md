# Gooey 0.4.0 Showcase

## Status

Proposal. Nothing here is implemented except a GitHub Pages workflow prototype
(`.github/workflows/pages.yml`) that builds today's `zig build wasm` output into a Pages
artifact on pull requests and never deploys until Duane enables Pages. The decisions this
proposal needs are listed at the end ("Decisions for Duane"). Parent plan:
`docs/v0.4.0-plan.md`; API: `docs/v0.4.0-core-contract.md`.

## Summary

- **One app teaches Gooey.** The showcase is a tutorial written in Gooey against the 0.4.0
  core: 22 chapters in five parts, each with prose, code samples, and live demos. Every
  Gooey feature lands in a chapter (feature checklist below).
- **The code you read is the code that runs.** Code samples are regions of the demo source
  files, extracted at comptime with `@embedFile`. Prose is comptime data in the binary.
  Nothing is loaded or allocated at run time.
- **Examples shrink from 31 files to 2 plus the 3 out-of-scope AI files.** Each phase 4
  cluster PR adds its chapter and deletes the examples that chapter replaces, after their
  0.3.1 goldens are captured. `disktree` stays as the stress case; `showcase` takes over
  `zig build run`, `wasm`, the Pages site, the preview skill, and the typecheck roots.
- **The core needs eleven small changes** (C1–C11) that the contract did not have, mostly
  for text and navigation: wrapped text, inline runs, a monospace family, external links,
  a location event, programmatic scroll, scoped demo state, viewport and capability
  queries, accessibility fields, an exception to rule 1 for the web's single thread, and
  runtime theme switching. Three are settled: the monospace family (contract decision 8),
  wrapped text, and the web's single thread (both decision 9). The others need Duane's
  ruling.
- **Web first.** The site is `zig build wasm` deployed by a Pages workflow, with hash deep
  links (`#/layout/sizing`). The first useful slice runs two chapters on `TestBackend` and
  macOS and needs one core change: wrapped text.

## Goals

1. Teach the nine core blocks in order, so a reader (human or agent) can write a Gooey app
   after reading the first five chapters.
2. Demonstrate every feature live, next to its explanation, on every platform that has it.
3. Replace examples whose only job is feature coverage, without losing test, benchmark, CI,
   or preview-skill coverage (Phase A policy).
4. Host the WebAssembly build as the project's public site.
5. Obey CLAUDE.md in the app itself: one declared budget, nothing allocated after init,
   every loop bounded. The showcase is also the largest real consumer of the core, so it
   is the first place the core's budgets are tested at scale.

Not goals: an API reference generated from doc comments (Zig's `-femit-docs` does that), a
Markdown renderer, a blog engine, or search across external content.

### 2.4 Prose, code, and links

**Chapters are Zig files.** Each chapter is `src/showcase/chapters/<nn>_<route>.zig` and
exports one comptime `Chapter`:

```zig
const doc = @import("../doc.zig");
const RowDemo = @import("../demos/layout_row.zig");

pub const chapter: doc.Chapter = .{
    .route = "layout",
    .title = "Layout",
    .blocks = &.{
        doc.heading(.h2, "Rows and columns", "rows"),
        doc.prose(
            \\A box lays out its children in a **column** unless its style says
            \\`.direction = .row`. Colours come from [the theme](#/elements/tokens).
        ),
        doc.demo(RowDemo),
        doc.source(RowDemo, "row"),
        doc.note(.native_only, "Liquid glass needs macOS 26."),
    },
};
```

Zig files over Markdown files: there is no block parser to write or bound, a typo in a
demo name or block kind is a compile error at the line, and demos are referenced by type.
The cost is that chapters do not render as documents on GitHub; the static HTML export in
S5 covers readers without WebGPU.

**Inline markup.** `doc.prose` accepts paragraphs separated by blank lines and four inline
forms: `**bold**`, `*italic*`, `` `code` ``, and `[label](target)`. A comptime parser turns
each paragraph into a `[]const Run` (byte range, style, optional link) stored in rodata.
Rendering a paragraph is one `ui.text` with runs (C2) and wrapping (C1). Until C2 lands, a
paragraph renders in one style and the parser rejects inline markup with a compile error
naming the chapter, so no chapter silently loses formatting; links meanwhile are their own
block (`doc.link`), rendered as a row of link buttons under the paragraph.

**Code samples come from demo source.** Every demo file embeds itself
(`pub const source = @embedFile("layout_row.zig");`) and marks regions with
`// region: row` and `// endregion`. `doc.source(Demo, "row")` extracts the region at
comptime, strips the markers, and removes the common indentation. A missing region, a line
over 100 columns, or a sample over 60 lines is a compile error. Because the region is the
demo's own code, every sample compiles and matches the running demo. A sample renders in
the mono family (`Text.family = .mono`, contract decision 8) without wrapping, scrolls
horizontally, and has a copy button (clipboard effect, P4).

**Highlighting runs at render time over visible lines.** Zig has no block comments and its
multiline strings are line-local, so a line can be tokenized alone. `std.zig.Tokenizer`
runs over each visible line (at most 100 bytes, so at most 100 runs); token tags map to
keyword, builtin, string, number, and identifier classes, the bytes between tokens are
whitespace or a comment, and the theme maps classes to colours. Nothing is stored per
sample, and no tokenizer state crosses lines. Comptime highlighting was rejected: about
4 bytes per token across ~60 samples is ~150 KiB of rodata for work that costs
microseconds per frame.

**Links.** Three kinds, parsed and checked at comptime:

- `#/route/section`: internal. Every target must name an existing chapter and heading
  anchor across all chapters, or the build fails with both names. Activating it sets the
  route in `State` and requests navigation (C5).
- `#section`: an anchor in the same chapter. Activating it scrolls the chapter column to
  the heading (C6).
- `https://…`: external. Only `https` is accepted. Activating it calls
  `effects.openUrl` (C4), which opens a new browser tab on the web and the default browser
  on native.

**Static allocation.** The content is comptime data in rodata; nothing is copied into Gooey
storage except what the core copies during build. The bounds are comptime asserts in
`doc.zig`:

| Bound | Value | Why |
| --- | ---: | --- |
| `chapter_count_max` | 32 | 22 planned, room for the reference part |
| `block_count_chapter_max` | 256 | The longest planned chapter has ~120 blocks |
| `prose_bytes_chapter_max` | 32 KiB | ~5,000 words |
| `paragraph_bytes_max` | 2 KiB | One paragraph is one text element |
| `run_count_paragraph_max` | 64 | Inline styles and links per paragraph |
| `source_line_count_max` | 60 | One sample fits one screen |
| `source_columns_max` | 100 | CLAUDE.md §25 |
| `link_count_chapter_max` | 128 | Hit records stay a small share of the budget |

A chapter is built whole every frame: at most 256 blocks is about 1,000 elements and
32 KiB of text copied into the frame (`text_bytes_frame_max` is 256 KiB at `standard`).
Layout at 65–83 ns per node is under 0.1 ms. Only what is inside the scroll clip may emit
glyph sprites, which needs emit-time culling (G2). Virtualizing the chapter through `List`
was considered and rejected for now: it needs height estimates for wrapped paragraphs that
have not been built, and the full build is already bounded and cheap.

### 2.5 Demos

A demo is a file in `src/showcase/demos/` with a `State`, a `render`, and its own
`App(State, render, .{ ... })` declaration, so it runs standalone
(`zig build run-demo -Ddemo=counter`) and inside a chapter. Embedded, the showcase stores
the demo's `State` as an entity and renders it through a state scope (C7): inside
`cx.scope(handle, Demo.render)`, `cx.state(Demo.State)` and `cx.on(Demo.State.method,
.{})` resolve to that entity. Demo code is then exactly the code a reader would write for
an app, which is the point of the tutorial. Without C7, demos target their entity
explicitly (`.entity = handle`), and chapter 1 has to explain entities before the counter.

Each demo carries its own golden trace on `TestBackend`, and each chapter has one golden
of the reader with that chapter open. These replace the examples' goldens and keep the
profile measurements reproducible (section 1).

### 2.6 Resource budget

The showcase declares one budget at its `gooey.App`, derived from `standard`:

```zig
pub const limits: gooey.ResourceLimits = blk: {
    var budget = gooey.ResourceLimits.standard;
    // Reader worst case is ~6,750 glyphs (sketch below); 16,384 keeps 2x headroom.
    budget.scene.glyph_count_frame_max = 16_384;
    // Chapter 8 holds the most text engines: 8 inputs, 1 area, 1 editor.
    budget.text.input.count_max = 16;
    budget.text.area.count_max = 2;
    budget.text.editor = .{ .count_max = 1, .bytes_max = 64 * 1024, .undo_depth_max = 128 };
    // ~20 demo entity types; the largest (todo, list rows) needs 64.
    budget.entities.count_per_type_max = 64;
    break :blk budget;
};
```

Fonts (contract decision 8): the app family is the platform sans-serif (`.font = null`),
and code samples use the platform monospace family as the second family, with the
`standard` faces plus mono regular and bold, 8 faces:

```zig
.font_mono = .{ .system = .monospace },
.font_limits = .{
    .variants = gooey.FontLimits.standard.variants,
    .mono_variants = &.{ .regular, .bold },
},
```

Atlases stay at `standard` (text 2048², SVG 1024², image 1024²); the icon chapter shows 48
icons, and the full Lucide grid stays in `lucide_demo` at `large`. The window budget stays
at 3840x2400 device pixels; the web host clamps the canvas backing store to it (G17).

Performance sketch (§7), worst case per frame at 1920x1200 logical pixels:

| Resource | Worst case | Limit | Notes |
| --- | ---: | ---: | --- |
| Prose glyphs | 4,250 | | 50 lines × 85 columns in the 720 px column |
| Sidebar and outline glyphs | 1,000 | | 50 rows × 20 |
| Demo glyphs | 1,500 | | The control gallery |
| **Glyph sprites** | **6,750** | 16,384 | Needs culling to the scroll clip |
| Elements | ~1,900 | 4,096 | 256 blocks × ~4, demo ≤ 600, chrome ≤ 300 |
| Text bytes copied in build | ≤ 48 KiB | 256 KiB | Chapter 32 KiB plus chrome and demo |
| Hit records | ≤ 500 | 4,096 | Links, controls, sidebar rows |
| Highlighting | ≤ 5,000 token steps | | 50 visible lines × 100 bytes |
| Events per tick | ≤ 256 | 256 | Pointer moves and scroll coalesce |

Memory: the core reserves 13.4 MiB of CPU memory at `standard` (milestone 1 measurement).
The larger glyph budget adds about 1 MiB across the two record buffers, and the editor
slot 64 KiB plus its undo history. Static content is about 220 KiB of rodata (22 chapters
at a 10 KiB planning average) under a comptime ceiling of 1 MiB (32 chapters × 32 KiB).
On the web, linear memory is estimated at 25–35 MiB including CPU copies of the atlases;
S2 measures it.

G17 in detail, the web work the site depends on:

- The browser has one thread, so the web host calls the combined `tick` (which already
  exists for headless use) from `requestAnimationFrame`: drain, build, layout, emit, pack,
  and draw in one callback.
- The JavaScript input rings feed the `EventQueue`; the hidden IME input answers through
  `Query`, as `firstRectForCharacterRange` does on macOS.
- The WebGPU renderer sits behind the pack stage like Metal; until phase 5 it consumes
  today's `Scene`.
- The canvas backing store is clamped to `limits.window.framebuffer_*_max`, and a
  `devicePixelRatio` change is a window event. Today `web/index.html` clamps to 8192.
- Wheel deltas are normalized for line and page modes. Touch input does not exist today
  (`web/index.html` listens for mouse and wheel only); pointer events would add it.
- Fonts must be ready before the first measurement (`document.fonts.ready`), or wrapped
  layout shifts when a late font replaces the fallback.
- The accessibility bridge builds its hidden DOM from the core's accessibility records.

G19: prose drawn on a canvas cannot be selected, searched with Ctrl+F, or translated by the
browser. Code samples get a copy button; the static HTML export (S5) is the full answer.
Selectable read-only text is a possible later core feature, not proposed for 0.4.0.

### 3.2 Contract changes for Duane

Each would be recorded under the contract's "Approved decisions" once ruled on.

- **C1. `Text` gains `wrap`, `line_height`, and `alignment`.** Approved as contract
  decision 9, as proposed: `wrap: enum { none, words, newlines } = .none`,
  `line_height: ?u16` (percent of the font's line height; null keeps the font's), and
  `alignment: enum { left, center, right } = .left`. The layout engine already wraps
  (`TextConfig.wrap_mode`); the core stops passing `.none` and emit writes one glyph run
  per wrapped line, counted against the same glyph and record limits as any other text.
- **C2. Inline runs in one text element.** Proposed: `ui.text` accepts `runs: []const Run`
  in its style, where a run is `{ length, weight, italic, color, family, link }` and `link`
  is an optional `Handler`. Layout wraps across runs as one paragraph; emit writes one hit
  record per wrapped fragment of a linked run, keyed by run index under the text's id.
  The alternative, a library component that lays words out itself, needs measurements and
  hit testing inside `ui.paint`, which is the "component reaches into `Window`" smell the
  plan uses as its completeness test. Without C2, prose styling is per paragraph only.
- **C3. A second font family.** Settled as contract decision 8, reframed: 0.3.1 already
  loads a monospace family as the app's only font, so the new part is a second family in
  the same frame. The core restores `.font`, `.font_size`, and `setFont`, and adds an
  optional `font_mono: ?FontSource`, `Text.family: enum { app, mono } = .app`, mono
  variants in `FontLimits` (empty in every profile, so apps without `font_mono` reserve
  nothing), and `Config.font_limits` to choose them. The code editor engine uses the same
  family.
- **C4. `Effects.openUrl(url: []const u8)`.** `Effects` is closed in §4. The URL is copied
  at the call (rule 6); `https` only, asserted. Web: `window.open(url, "_blank",
  "noopener")`. macOS: `NSWorkspace openURL`. Linux: the OpenURI portal. Windows:
  `ShellExecuteW`.
- **C5. Navigation.** `Config` gains `on_navigate: ?*const fn (state: *State, route:
  []const u8, effects: *Effects) void`, invoked from drain for the initial route, for
  `hashchange` and `popstate` on the web, and for `--route` on native. `Effects` gains
  `navigate(.{ .route, .title, .mode = .push | .replace })`, which updates the address bar,
  history, and document title on the web and does nothing else on native. Both `Config`
  and `Effects` are closed in the contract.
- **C6. App-controlled scroll.** The contract retains scroll offsets by the box's key, and
  there is no keep-alive. The showcase must restore a chapter's scroll position when the
  reader returns and jump to anchors. Proposed: `Scroll` gains an optional
  `offset: ?*f32` bound to app state (as `TextInput.bind` is), and `Effects` gains
  `scrollTo(id, .{ .align = .start | .center | .nearest })`, applied after the next layout.
- **C7. State scopes.** `cx.scope(handle, render_fn)` renders `render_fn` with `handle` as
  the target of `cx.state(T)` and of `cx.on` for methods on `T` (the handle's type), so a
  standalone app's render function runs unchanged inside another app. `cx.on` keeps its
  Debug type check; the scope only changes which target matches. Section 2.5 explains why.
- **C8. Read-only queries in `Cx`.** `cx.viewport()` returns the window's logical size, so
  the reader can collapse its sidebar on narrow windows and phones; `percent` sizing cannot
  change structure. `cx.capabilities()` returns what the platform offers (multiple
  windows, glass, custom shaders, native dialogs, the platform name), so chapters choose a
  live demo or a note at run time.
- **C9. Accessibility fields.** `A11y` gains `heading_level` (the existing
  `accessibility.HeadingLevel`), `live: enum { off, polite, assertive }`, and
  `href: ?[]const u8` for links, so the web bridge emits `<a href>` and screen-reader link
  lists and native activation work. `Effects` gains `announce(text, politeness)`.
  `accessible_form` uses live regions today; the core has none.
- **C10. One thread on the web.** Approved as contract decision 9 and noted under rule 1:
  the browser host runs drain, build, layout, emit, pack, and draw in sequence inside each
  `requestAnimationFrame` callback. The `built` and `presented` buffers still swap at the
  end of a frame, so the core code is the same on every platform; only the web host has no
  render thread.
- **C11. Runtime theme switching.** `config.theme` is a constant pointer. Proposed:
  `Effects.setTheme(theme: *const Theme)`, applied at the next build. Today's showcase and
  dashboard toggle themes.

**`render` is settled.** It is passed to `App` positionally, as in 0.3.1:
`gooey.App(State, render, .{ ... })` (contract §7 and approved decision 7). That is
explicit, which is what the showcase needs in two places: each standalone demo exports its
own `render` and its own `App(Demo.State, Demo.render, .{ ... })` (section 2.5), and
opening a second window in chapter 17 takes a render argument the same way (G18). PR #112
applies decision 7 in code, with two other changes the showcase relies on: completion
handlers are named directly with `effects.handler(State.method)` (the file picker in
chapter 18), and clicks fire on release, so prose links and demo controls activate the
same way.

### 3.3 Suggested phase 4 order

The showcase reaches the public fastest, and each later cluster gets its chapter, if
phase 4 runs in this order:

1. **Web and Linux on the shared tick** (G17, C10). The web is the site; Linux is where orbs
   render previews and CI runs.
2. **Text, part 1: wrap, runs, the mono family** (C1, C2, decision 8). This unblocks
   every chapter.
3. **Scroll, clip, culling, app-controlled scroll** (G2, C6).
4. **Keymap and actions, timers and clipboard, links and navigation** (G8, G16, C4, C5).
5. **Entities and state scopes** (G9, C7), so demos can be written once.
6. Then the clusters in chapter order, each adding its chapter and cutting its examples:
   text engines (8), controls and layers (7, 10), drag and drop (11), lists (12), paint
   meshes, images, and colour glyphs (13, 14), charts (15), animation (16), multiple
   windows (17), accessibility fields (19, C9), shaders and glass (21).

Phase 4 follows this order with one refinement: work that needs no contract change goes
first. Linux moves onto the shared tick first, then the web (C10 is approved as decision
9). Steps 2–4 start as each C-item is ruled, and keymap, timers and clipboard, entities in
`Config`, and the text engines fill the gaps between them. S1 does not wait for Linux: it
needs only C1, approved as decision 9, and runs on `TestBackend` and macOS, so it can start
as soon as phase 4 lands wrapped text.

## 4. Web hosting

**Build.** The site is the output of `zig build wasm` (`addWasmExample`: ReleaseSmall,
1 MiB stack, `web/index.html`, assets). In S2 the `wasm` step's source switches from
`src/examples/showcase.zig` to the new showcase, and the output directory is the site. No
other build step is needed; `wasm-counter` is retired with `counter`.

**Workflow (prototype on this branch).** `.github/workflows/pages.yml`:

- `build` runs on pull requests that touch the web build, on pushes to `main`, and on
  manual dispatch. It runs `zig build wasm -Dskip-shader-compile=true`, writes the raw and
  gzip sizes of `app.wasm` and `index.html` to the job summary, and uploads `zig-out/web`
  with `actions/upload-pages-artifact`.
- `deploy` runs `actions/deploy-pages` only when the event is not a pull request and the
  repository variable `GOOEY_PAGES_ENABLED` is `true`. Until Duane enables Pages
  (Settings → Pages → Source: GitHub Actions) and sets the variable, it is skipped.
  Artifact deployments skip Jekyll, so no `.nojekyll` file is needed.
- Deploying from `main` publishes the 0.3.1 showcase until 0.4.0 merges. Previewing the
  core showcase from `integration/v0.4.0` needs that branch allowed in the `github-pages`
  environment (decision 13).

**Deep links.** Hash routes (`https://duanebester.github.io/gooey/#/layout/sizing`) work
on Pages with one `index.html`, because the server never sees the fragment. Path routes
(`/gooey/layout/sizing`) would need a copy of `index.html` per route and absolute asset
paths; their only advantage is per-route link previews, which a canvas app cannot fill
with content anyway. The host reads `location.hash` before the first frame, passes it to
`on_navigate`, and turns `hashchange` and `popstate` into navigation events (C5).

**Binary size.** Measured on this branch (ReleaseSmall, wasm32):

| Build | Raw | gzip -9 |
| --- | ---: | ---: |
| `wasm` (0.3.1 showcase) | 940,931 B | 145,017 B |
| `wasm-counter` (0.3.1 counter) | 295,271 B | 104,810 B |
| Core todo, headless (no renderer, no web host), scratch build | 152,524 B | 55,665 B |
| `web/index.html` | 82,577 B | 15,796 B |

Projection for the showcase on the core: the core, the WebGPU renderer and web host,
components, charts, and ~220 KiB of prose, about 1.0–1.4 MB raw and 250–350 KB gzip.
Proposed budget: 2 MiB raw and 512 KiB gzip for `app.wasm`, reported by the workflow from
S2 and enforced once the showcase is complete. No `wasm-opt`: it is an extra tool
(§26), and ReleaseSmall is the lever.

**Fonts.** The web text backend rasterizes with Canvas 2D and the CSS family
`system-ui, -apple-system, sans-serif` (`text/backends/web/face.zig`), so the site looks
like each reader's OS and is free. Bundling OFL fonts (for example Inter and JetBrains
Mono, roughly 150–300 KB as woff2) would make layout identical across systems and give
the code samples a known monospace face. Either way the host waits for `document.fonts.ready`
before the first measurement (decision 14).

**Accessibility.** The web bridge (`web/index.html`) mirrors the accessibility tree into
a hidden DOM with ARIA roles under a container with `role="application"`. That role
suits widgets but stops screen readers from reading prose in browse mode. For the site the
chapter column is `role="document"`, headings carry `aria-level`, links are `<a href>`
(C9), code samples are `<pre>`, and only demo panels are `role="application"`. DOM focus
follows core focus so the screen reader's cursor tracks Tab. VoiceOver in Safari and NVDA
in Firefox are the manual checks.

**Browsers without WebGPU.** The page shows the static HTML export of the requested
chapter (S5): the same prose and code samples, generated from the chapter data by a Zig
build program that imports `doc.zig`, with demos replaced by screenshots. Until S5 it shows
a message and a link to the repository.

**Mobile.** Touch input (G17) and a narrow layout (C8) arrive in S5; S2 targets desktop.

- **S0, this PR.** The design and the Pages workflow prototype. No framework or example
